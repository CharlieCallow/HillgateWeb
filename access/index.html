How it works

Web application and API access.

Two access channels are available to onboarded institutional counterparties. The web application is the primary channel. The Hillgate payment API has a deliberately limited surface and excludes actions that require manual review.

Access is granted only after onboarding is complete. No account functionality, including the web application and API keys, is accessible to a user before onboarding completion. Onboarding is mediated. There is no self-service registration.

To begin the onboarding process, use the Request institutional access form.

The two access channels

Web application

The primary channel. Authenticated browser session with role-based access for the institution's users.

Includes

  • Beneficiary management, including trusting and untrusting beneficiaries.
  • Payment initiation (Third-Party Payments).
  • FX quote, confirm and execute.
  • Settlement instruction within the Instant Settlement Network.
  • Crypto-asset custody operations (available following MiCAR authorisation).
  • Transaction history, statements, audit log export.
  • API key management, user and permission management, 2FA settings.
  • Network membership, opt-in and opt-out.

Excludes

  • Programmatic batch operations beyond the surface area exposed to API.

Hillgate payment API

An authenticated programmatic interface. The surface is intentionally narrow and excludes actions that require manual review.

Includes

  • Trading initiation (FX Trading: request quote, accept quote, execute).
  • Transfer instructions to previously trusted beneficiaries (fiat payments only).
  • Transaction information retrieval, statements and reconciliation endpoints.

Excludes

  • Trusting or untrusting a beneficiary. The beneficiary trusting workflow is web-app only.
  • Custody-related actions. Crypto-asset custody operations are web-app only and become available following MiCAR authorisation.
  • Account opening or change to account configuration.
  • Full product information, fees and risk disclosures. Those are read on this site, not retrieved through the API.
  • API onboarding. API keys are issued only after web-app onboarding is complete and a key is requested in the web application.

Choice environment

The counterparty chooses, at the point of onboarding, whether to use only the web application or to also enable API access. The choice can be revised at any time after onboarding.

  • Web application only: covers every action across every product, including those that the API does not support. This is the default and is sufficient for most institutional counterparties.
  • Web application plus API: adds programmatic access to the actions listed in the matrix above. The web application is still required for beneficiary trusting, custody operations and account configuration.

The fees schedule and the risk disclosure are publicly available so they can be read before any commitment to onboard. The licences page describes the legal regime under which each product is provided.

Onboarding gating

Access to the web application and to any API key is gated on onboarding completion. The onboarding process includes know-your-customer review, ultimate-beneficial-owner disclosures, source-of-funds evidence, sanctions screening, suitability assessment for each product the counterparty intends to use, and execution of the account agreement.

No login credentials are issued before onboarding is complete. The API has no public, pre-onboarding endpoints. The public site offers product information, fees, disclosures, and an enquiry form for prospective counterparties.
